# 2.0 — Arquitetura das APIs

## Decisão
O sistema será preparado para trabalhar com múltiplas APIs e diferentes países/regiões, evitando dependência direta de um único fornecedor.

## Fontes iniciais
Direção inicial:
- mercados/filiais: Google Places + segunda fonte aberta/confiável, como OpenStreetMap/Overpass;
- produtos: Open Food Facts e futuras fontes compatíveis;
- preços: Open Prices e outras fontes de preço que possam ser adicionadas por região.

A arquitetura é mundial. Fontes específicas poderão variar conforme o país.

## Banco próprio como núcleo
- Dados que pertencem ao nosso domínio e já existem no banco devem vir do banco.
- APIs servem principalmente para descobrir, atualizar, complementar e validar informações.
- Mercados e produtos descobertos externamente devem ser normalizados e persistidos no nosso banco.
- A interface não deve depender diretamente de uma API quando o dado pode ser servido pelo nosso sistema.

Fluxo principal:

`API externa → Provider/Adapter → Normalização/Validação → Banco próprio → Aplicação`

## Providers e adapters
Cada integração externa será isolada em um provider/adaptador próprio.

Exemplo:

`MarketProvider → GooglePlacesProvider / OpenStreetMapProvider`

Isso permite adicionar, substituir ou remover fornecedores sem reescrever o núcleo do sistema.

## Confiança e validação
As informações externas recebem um score interno de confiança.

Regra inicial:
- score **>= 50**: pode ser normalizado e salvo automaticamente;
- score **< 50**: deve ir para revisão do Admin antes de ser publicado.

O limite deverá ser configurável futuramente e poderá evoluir por tipo de dado.

Mudanças simples com alta confiança podem ser aplicadas automaticamente. Mudanças importantes, conflitantes ou de baixa confiança devem ir para revisão administrativa.

## Frequência padrão de atualização
- **Mercados:** a cada 15 dias.
- **Produtos:** a cada 7 dias.
- **Preços:** diariamente.

Essas frequências são padrões configuráveis. Providers ou tipos de dados específicos poderão exigir políticas diferentes.

## Falha de API
Uma falha externa nunca deve apagar um dado válido existente.

Quando uma API falhar:
1. manter o último dado válido no banco;
2. continuar atendendo o usuário com esse dado;
3. mostrar discretamente a idade da informação, por exemplo `Atualizado há 3 dias`;
4. registrar a falha;
5. tentar sincronizar novamente;
6. alertar o Admin se a falha persistir ou ultrapassar limites definidos.

O sistema terá acompanhamento de saúde das integrações para identificar APIs problemáticas e dados desatualizados.

## Controle de custo e limites
Para APIs pagas ou limitadas:
- cache para evitar chamadas repetidas;
- cotas por integração;
- controle de chamadas diárias/mensais;
- teto de gasto configurável;
- alertas antes de atingir limites;
- preferência por dados já persistidos no banco;
- uso de fonte alternativa quando disponível.

Direção de fallback:

`Banco → Provider principal → Provider alternativo → alerta ao Admin`

## Proveniência dos dados
Devemos registrar a origem dos dados relevantes, incluindo:
- provider/fonte;
- momento da coleta;
- referência externa quando disponível;
- confiança associada quando aplicável.

Isso permite auditoria, resolução de conflitos, revalidação e revisão administrativa.

## Admin e integrações
O Admin poderá:
- ativar/desativar providers;
- acompanhar saúde da integração;
- ver última sincronização;
- acompanhar falhas recentes;
- acompanhar volume de chamadas/uso;
- receber alertas de falhas persistentes, limites e dados desatualizados.

## Segurança
**Credenciais, tokens e chaves de APIs externas são obrigatoriamente server-side.**

Elas nunca devem ser expostas no frontend/aplicativo do usuário. Chamadas que necessitem segredos passam por backend/serviços seguros, com as credenciais armazenadas em variáveis/secret management apropriados.

## Princípio final
**Nosso banco é o núcleo operacional; APIs são providers substituíveis de descoberta, atualização e validação. Toda integração deve ser observável, controlável, segura e tolerante a falhas.**
