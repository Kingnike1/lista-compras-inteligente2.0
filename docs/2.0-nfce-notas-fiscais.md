# 2.0 — NFC-e e Notas Fiscais

## Objetivo
Usar notas fiscais como evidência real de compras para melhorar histórico de compras, catálogo e preços sem coletar dados pessoais desnecessários.

## Entrada da nota
O sistema terá três caminhos:
1. **QR Code da NFC-e** como fluxo principal;
2. foto/PDF da nota como alternativa;
3. chave de acesso como alternativa manual.

O fluxo deve privilegiar o menor esforço possível para o usuário.

## Fluxo
`nota recebida → validação → identificação da filial → leitura dos itens → correspondência com catálogo → registro da compra → histórico de preços`

A nota é uma evidência. Ela não possui autorização irrestrita para alterar a base global.

## Correspondência com catálogo
- Correspondências fortes podem ser processadas automaticamente conforme o Sistema de Confiança.
- Descrições fiscais ambíguas, produtos não identificados ou conflitos vão para investigação/revisão.
- IA pode auxiliar na interpretação da descrição fiscal, mas não pode inventar EAN/GTIN, produto, filial, preço ou vínculo.

## Preços
Uma compra validada pode comprovar que determinado produto foi comprado por determinado preço naquela filial e naquele momento.

Esse registro alimenta o histórico, mas **não significa automaticamente que o mesmo preço continua vigente hoje**.

As regras de atualidade, confiança e preço-base seguem a arquitetura de preços 2.0.

## Privacidade por minimização
O sistema deve extrair e compartilhar apenas os dados necessários para sua função.

Dados que podem alimentar a base compartilhada:
- produto identificado;
- filial;
- preço;
- quantidade/unidade necessária para interpretar o preço;
- data/hora da compra.

Dados pessoais, sensíveis ou desnecessários devem ser **ignorados e não persistidos sempre que não forem necessários**.

Exemplos que não devem alimentar a base compartilhada:
- CPF do consumidor;
- dados de pagamento;
- informações pessoais sem finalidade operacional;
- outros campos fiscais que não sejam necessários ao funcionamento do produto.

O princípio é: **não coletar o que não precisamos**, em vez de coletar tudo e tentar proteger depois.

## Nota original e evidência
Quando tecnicamente necessário manter uma evidência original para uma funcionalidade privada, ela deve permanecer restrita ao contexto autorizado do usuário/casa e nunca virar dado público/global.

Sempre que for possível cumprir a finalidade sem guardar o documento integral, deve-se preferir armazenar somente os dados estruturados necessários e a proveniência técnica mínima.

## Auditoria e correções
Dados históricos confirmados não devem ser silenciosamente sobrescritos ou destruídos. Correções devem preservar rastreabilidade e indicar que um registro anterior foi corrigido, invalidado ou substituído.

## Falhas
Se QR Code, consulta estruturada ou leitura automática falhar:
- tentar os métodos alternativos disponíveis;
- não inventar campos ausentes;
- permitir revisão quando necessário;
- manter o restante do aplicativo funcionando normalmente.

## Escala internacional
NFC-e é um mecanismo brasileiro, mas o domínio deve ser modelado genericamente como **receipts / comprovantes fiscais**, permitindo adapters específicos por país e tipo de documento.

Assim, o núcleo trabalha com um modelo normalizado de compra e cada integração regional interpreta seu próprio documento fiscal.

## Papel do Admin
O Admin atua principalmente nas exceções:
- correspondências incertas;
- produtos não reconhecidos;
- filial não identificada;
- dados conflitantes;
- suspeita de informação incorreta;
- revisão exigida pelo Sistema de Confiança.

Casos suficientemente confiáveis podem seguir automaticamente.

## Princípio final
**A nota fiscal serve para comprovar a compra e enriquecer o sistema com fatos úteis, não para transformar dados pessoais do consumidor em dados da plataforma. Extraímos o mínimo necessário, compartilhamos apenas dados não sensíveis úteis ao produto e usamos confiança + Admin para controlar exceções.**
