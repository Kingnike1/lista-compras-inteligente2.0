# 2.0 — Preços

## Decisão
Preço é um dado central do sistema e deve representar o **valor real praticado do produto em uma filial específica**, separado de promoções e condições especiais.

## Preço-base
- O preço-base representa o valor normal/praticado do produto.
- Promoções não substituem o preço-base.
- Preços promocionais, de clube, aplicativo ou condições especiais ficam registrados separadamente.
- Isso permite comparar o preço normal com ofertas sem distorcer o histórico.

## Escopo do preço
O preço pertence à combinação:

`produto + filial`

Duas filiais da mesma rede podem ter preços diferentes para o mesmo SKU.

## Preço atual e histórico
- O preço atual é o **registro válido mais recente** daquele produto naquela filial.
- Registros anteriores nunca são sobrescritos ou apagados apenas porque chegou um novo preço.
- O histórico deve preservar data/hora, origem e contexto do valor coletado.

Isso permite análises futuras de aumento, queda, tendência e qualidade de promoções.

## Atualização e validade
A política operacional definida na Arquitetura de APIs é de tentativa de atualização diária para preços.

Para experiência e confiança:
- até 3 dias desde a última observação válida: preço tratado como atual;
- acima de 3 dias: continua disponível, mas é marcado como desatualizado;
- o usuário verá uma informação discreta como `Atualizado há 5 dias`.

Preço antigo não deve ser apagado por falta temporária de atualização.

## Fontes aceitas
O sistema poderá receber preços de:
- APIs/providers externos confiáveis;
- NFC-e/notas fiscais validadas;
- parceiros/mercados confiáveis no futuro;
- contribuição manual do usuário, sempre sujeita a validação administrativa antes de entrar na base compartilhada.

## Preço informado pelo usuário
Um preço digitado manualmente pelo usuário **nunca vira preço oficial/global automaticamente**.

Fluxo:
1. usuário informa o preço;
2. o registro fica como contribuição pendente;
3. pode permanecer visível apenas no contexto privado da casa, quando útil;
4. Admin valida antes de promover esse valor para a base compartilhada.

## Confiança e anomalias
Os preços devem seguir o sistema de confiança da plataforma.

O sistema deverá detectar valores suspeitos ou discrepantes em relação ao histórico e a outras fontes. Casos com baixa confiança, conflito relevante ou alteração anormal devem ir para revisão, em vez de substituir automaticamente o preço confiável existente.

## Proveniência mínima
Cada observação de preço deve guardar, quando aplicável:
- `product_id`;
- `store_location_id`;
- valor;
- moeda;
- data/hora observada;
- fonte/provider;
- referência externa ou comprovante;
- confiança;
- tipo do preço (`base`, `promotion`, `club`, etc.);
- validade ou período da condição especial, quando conhecido.

## Arquitetura mundial
Como o 2.0 é pensado para operar em diferentes países, o preço nunca deve assumir uma moeda fixa no modelo de dados. Cada observação deve carregar sua moeda.

Comparações normais devem priorizar preços na mesma moeda/região. Conversão cambial, se necessária futuramente, será uma camada separada e não altera o valor original registrado.

## Falha de atualização
Se a fonte de preços estiver indisponível:
- manter o último valor válido;
- não sobrescrever por ausência de resposta;
- informar a idade do dado;
- registrar a falha de sincronização;
- alertar o Admin conforme as regras de saúde das integrações.

## Relação com promoções
Promoções são dados complementares ao preço-base.

Exemplo:
- preço-base: R$ 29,90;
- promoção: R$ 24,90;
- condição: válida até determinada data, quando conhecida.

O histórico do preço-base continua preservado. Isso prepara o sistema para futuramente avaliar se uma promoção representa economia real.

## Princípio final
**Preço é histórico, localizado por filial, rastreável pela fonte e separado de promoções. O sistema preserva o último dado confiável, sinaliza desatualização e nunca transforma contribuição manual ou valor suspeito em verdade global sem validação.**
